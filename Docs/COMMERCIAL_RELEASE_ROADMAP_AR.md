# خطة الوصول إلى الإطلاق التجاري — AquaFarm Pro

**الإصدار:** 1.0  
**تاريخ الأساس:** 12 يوليو 2026  
**أفق الخطة:** 26–34 أسبوعاً  
**حالة المشروع عند البداية:** نموذج أولي متقدم؛ غير معتمد بعد كنظام محاسبي أو حل فوترة إلكترونية متوافق مع ZATCA.

## 1. الهدف ونطاق الإطلاق

الهدف هو إصدار تجاري مستقر لمزرعة واحدة أو عدة مزارع، يدعم التشغيل اليومي، المحاسبة مزدوجة القيد، الفوترة الإلكترونية السعودية، أمن البيانات، النسخ الاحتياطي، الدعم والتحديث، مع أدلة اختبار وامتثال قابلة للمراجعة.

ينقسم المنتج إلى مستويين، ولا يجوز الخلط بينهما:

1. **الإطلاق التشغيلي المحدود:** تشغيل وحدات المزرعة والمخزون والمبيعات، مع استمرار المحاسبة والفوترة النظامية في حل خارجي معتمد.
2. **الإطلاق التجاري الكامل:** اعتماد النظام كسجل تشغيلي ومحاسبي أساسي، بعد اجتياز بوابات المحاسبة وZATCA والأمن والتشغيل.

## 2. مبادئ الحوكمة

- لا تُغلق أي مهمة بعبارة «تم» من دون دليل: اختبار ناجح، لقطة/تقرير، مراجعة كود، أو توقيع قبول.
- لكل متطلب: مالك، تاريخ مستهدف، معيار قبول، دليل، وحالة.
- لا تُسوّق عبارات «متوافق مع SOCPA/IFRS/ZATCA/ISO» قبل إكمال مصفوفة الامتثال واعتماد المختص المناسب.
- أي عيب يمس سلامة القيد أو الضريبة أو فقد البيانات يصنف `P0` ويمنع الإصدار.
- يتم تجميد نطاق الإصدار قبل الاختبار التجريبي بأربعة أسابيع؛ لا تُقبل ميزات جديدة إلا لمعالجة عيب مانع.

## 3. هيكل المسؤوليات المقترح

| الدور | المسؤولية الأساسية | الحد الأدنى للتفرغ |
|---|---|---:|
| مالك المنتج | النطاق والأولويات وقبول الأعمال | 30% |
| قائد تقني/.NET | المعمارية والمراجعة والإصدارات | 100% |
| مطور Backend/Accounting | دفتر الأستاذ، الضرائب، التكامل | 100% |
| مطور WinForms/UX | الواجهات والتقارير وتجربة المستخدم | 100% |
| مهندس QA | خطة الاختبار والأتمتة وUAT | 100% من الأسبوع 5 |
| محاسب سعودي مرخص | السياسات، دليل الحسابات، IFRS/SOCPA | 20–40% |
| مختص ZATCA | XML والتوقيع والاختبارات والربط | حسب المرحلة |
| مختص أمن/PDPL | التهديدات، الاختبار، الخصوصية | نقاط مراجعة دورية |
| مسؤول تشغيل ودعم | التثبيت والمراقبة والنسخ والدعم | 50% من الأسبوع 12 |

إذا كان الفريق أصغر من ذلك، يزداد الزمن ولا تُدمج مسؤولية قبول المحاسبة مع مسؤولية كتابة الكود نفسه.

## 5. الخطة المرحلية

### المرحلة 0 — تأسيس البرنامج وضبط خط الأساس

**المدة:** أسبوعان  
**الهدف:** جعل حالة المشروع قابلة للقياس وإزالة الغموض حول ما يعمل فعلاً.

#### الأعمال

- إنشاء سجل متطلبات موحد، وسجل مخاطر، وسجل قرارات معمارية.
- جرد جميع الشاشات والوظائف وتصنيفها: مكتملة، جزئية، وهمية، غير مستخدمة.
- حصر الرسائل والـTODO والقيم الثابتة والعمليات التي تبتلع الاستثناءات.
- إصلاح صلاحيات ملفات `bin/obj` وإثبات بناء Release من نسخة نظيفة.
- توحيد الوثائق على SQLite أو اتخاذ قرار موثق بالانتقال إلى قاعدة خادم.
- تحديد نطاق الإصدار الأول بوضوح: جهاز واحد، شبكة محلية، أم فروع متعددة.
- تعريف البيئات: Development وTest وUAT وProduction.
- اعتماد ترقيم الإصدارات، سياسة الفروع، مراجعة الكود، وتعريف Done.
- إنشاء قائمة تراخيص الحزم والأصول والخطوط.

#### المخرجات

- Product Backlog مرقم.
- مصفوفة تتبع: `REQ → Design → Code → Test → Evidence`.
- تقرير بناء واختبار أساسي.
- وثيقة نطاق وإطار دعم.
- قائمة مخاطر مرتبة بالاحتمال والأثر.

#### بوابة القبول G0

- بناء Release ناجح من جهاز/عامل نظيف.
- كل ميزة حرجة لها متطلب ومعيار قبول ومالك.
- لا توجد وظيفة مصنفة «مكتملة» من دون اختبار أو دليل.
- قرار قاعدة البيانات ونموذج النشر معتمد.

### المرحلة 1 — تثبيت الأساس التقني والأمن الأولي

**المدة:** 3–4 أسابيع  
**الهدف:** إزالة مخاطر فقد البيانات والتكوين غير الآمن قبل توسيع الوظائف.

#### الأعمال التقنية

- إزالة قواعد البيانات والنسخ الاحتياطية والسجلات الحساسة من حزمة المصدر والإصدار.
- نقل جميع الإعدادات والأسرار إلى إعدادات بيئية آمنة؛ منع القيم الضريبية الوهمية في الإنتاج.
- توحيد مسار قاعدة البيانات بين التطبيق وخدمة النسخ الاحتياطي.
- استخدام SQLite Online Backup أو آلية متسقة، مع تشفير النسخ ونقل نسخة خارج الجهاز.
- إضافة فحوص بدء التشغيل: صلاحية المجلد، المساحة، سلامة المخطط، الإصدار، والهجرة.
- إضافة سجل تدقيق منظم للأحداث الأمنية والإدارية.
- فرض BCrypt فقط وترحيل أي hash قديم؛ منع كلمات المرور الافتراضية.
- تطبيق سياسة كلمة مرور، قفل دائم/مؤقت مدعوم بقاعدة البيانات، وانتهاء جلسة فعلي.
- إعداد CI للبناء والاختبار وفحص الحزم والثغرات.
- إضافة معالجة مركزية للأخطاء مع رقم تتبع دون كشف بيانات حساسة للمستخدم.

#### الاختبارات

- تثبيت نظيف، ترقية، إزالة، واستعادة بعد فشل ترقية.
- انقطاع مفاجئ أثناء الحفظ.
- نسخة احتياطية أثناء وجود نشاط، ثم استعادتها والتحقق من سلامة البيانات.
- محاولات دخول، تجاوز صلاحيات، وتغيير دور المستخدم.

#### بوابة القبول G1

- ثلاثة اختبارات استعادة متتالية ناجحة.
- لا أسرار أو بيانات شخصية أو كلمات مرور افتراضية في الحزمة.
- CI أخضر لخمسة تشغيلات متتالية.
- صفر ثغرات حرجة أو عالية معروفة.

### المرحلة 2 — بناء النواة المحاسبية مزدوجة القيد

**المدة:** 6–8 أسابيع  
**الهدف:** تحويل التقارير المجمعة إلى نظام محاسبي قابل للمراجعة.

#### نموذج البيانات المطلوب

- دليل الحسابات الهرمي، نوع الحساب، طبيعته، العملة، وحالة الاستخدام.
- الفترات والسنوات المالية وحالات الفتح/الإقفال.
- رأس القيد وأسطر القيد: الحساب، المدين، الدائن، مركز التكلفة، المرجع والمصدر.
- قيود مسودة/معتمدة/مرحلة/معكوسة، مع منع تعديل القيد المرحل.
- مراكز تكلفة: مزرعة، حوض، دورة إنتاج، قسم.
- أرصدة افتتاحية وتسويات وإقفال الأرباح والخسائر.
- سجل تدقيق بالقيمة السابقة والجديدة والمستخدم والسبب والوقت.

#### قواعد الأعمال

- مجموع المدين يساوي الدائن قبل الترحيل.
- أرقام قيود متسلسلة وفريدة وغير قابلة لإعادة الاستخدام.
- منع الترحيل إلى فترة مقفلة.
- إلغاء العملية بقيد عكسي، لا بحذف الأثر.
- فصل إنشاء القيد عن اعتماده وفق حدود مالية.
- خرائط ترحيل للمبيعات والمشتريات والمخزون والرواتب والإهلاك والتحصيل والسداد وVAT.

#### المحاسبة القطاعية والمعايير

- إعداد سياسة IAS 41 للأصول البيولوجية للأسماك والتحول البيولوجي.
- دعم القيمة العادلة ناقص تكاليف البيع أو توثيق سبب عدم إمكان القياس عند انطباق الاستثناء.
- معالجة IAS 2 للمخزون بعد الحصاد؛ لا يسمح بـLIFO في تقارير IFRS.
- IAS 16 للأصول والإهلاك والانخفاض.
- IFRS 15 للإيراد، IFRS 9 للذمم والخسائر الائتمانية عند انطباقه.
- تصميم القوائم والإيضاحات وفق SOCPA والمعايير المعتمدة في المملكة، مع مراعاة IFRS 18 في موعد تطبيقه.

#### الاختبارات الإلزامية

- 100 سيناريو قيد على الأقل تشمل دورة البيع والشراء والرواتب والمخزون والإهلاك والمرتجعات.
- مطابقة ميزان المراجعة مع الأستاذ العام في كل تشغيل.
- إقفال وفتح سنة، قيد عكسي، وفترة مقفلة.
- اختبار حدود التقريب والعملات والقيم السالبة والتواريخ العابرة للسنوات.
- مقارنة عينة شهر كامل بحساب يدوي معتمد من المحاسب.

#### بوابة القبول G2

- توقيع المحاسب على السياسات ودليل الحسابات وخرائط الترحيل.
- صفر قيد غير متوازن في مليون سطر اختبار مولّد.
- القوائم مصدرها الأستاذ العام فقط، بلا أرصدة ثابتة أو حسابات جانبية.
- تطابق العينة المحاسبية المعتمدة بفارق لا يتجاوز 0.01 ريال لكل قيد.

### المرحلة 3 — المخزون والتكلفة والتتبع التشغيلي

**المدة:** 4–5 أسابيع، ويمكن تداخلها جزئياً مع المرحلة 2  
**الهدف:** ضمان أن العمليات المادية والمالية متسقة وقابلة للتتبع.

#### الأعمال

- إكمال استلام المشتريات وحركات المخزون ضمن معاملة قاعدة بيانات واحدة.
- منع المخزون السالب أو تعريف سياسة معتمدة له.
- اعتماد FIFO أو المتوسط المرجح وفق السياسة؛ إزالة LIFO من أي ادعاء IFRS.
- جرد دوري وكامل، فروقات جرد بموافقة وقيد محاسبي تلقائي.
- تتبع الدفعة/الحوض/الدورة من الأعلاف والمدخلات حتى البيع.
- حساب تكلفة الوحدة والنفوق والتحويلات والمنتج عند الحصاد.
- تسويات تلقائية بين دفتر المخزون والأستاذ العام.
- صلاحيات وموافقات لأوامر الشراء والاستلام والفروقات.

#### بوابة القبول G3

- تطابق كمية وقيمة المخزون التشغيلي مع الأستاذ في 100% من سيناريوهات الاختبار.
- تتبع أمامي وخلفي لدفعة خلال أقل من 15 دقيقة.
- فروق عينة الجرد التجريبي ≤ 1%، وكل فرق له سبب وموافقة وقيد.

### المرحلة 4 — ZATCA والضرائب السعودية

**المدة:** 5–7 أسابيع  
**الهدف:** تنفيذ الفوترة الإلكترونية والضريبة كمكوّن نظامي لا كـPDF فقط.

#### الأعمال

- فصل B2B Tax Invoice عن B2C Simplified Tax Invoice والإشعارات الدائنة والمدينة.
- توليد UBL 2.1 XML وفق قاموس ومواصفات ZATCA.
- UUID، Invoice Counter، Previous Invoice Hash، QR TLV، والتوقيع/الختم المطلوب.
- إدارة CSID: onboarding، renewal، revocation، sandbox، simulation، production.
- Clearance للفواتير القياسية وReporting للمبسطة حسب المتطلبات.
- Outbox موثوق: حفظ محلي، إعادة محاولة، idempotency، وحالات رفض واضحة.
- منع اعتبار الفاتورة «مقدمة» بمجرد تغيير حالة محلية.
- حفظ XML والاستجابة والـhash وحالة الهيئة بطريقة غير قابلة للتعديل.
- التعامل الصحيح مع المناطق الزمنية والتقريب والإعفاء والصفر والتصدير.
- مطابقة إقرار VAT مع الأستاذ والفواتير والإشعارات، لا مع إجماليات منفصلة.

#### الاختبارات

- كل عينات ZATCA الإيجابية والسلبية.
- انقطاع الشبكة، انتهاء الشهادة، التكرار، رفض XML، وإعادة الإرسال.
- تسلسل 10,000 فاتورة دون UUID أو counter مكرر.
- مطابقة الضريبة على مستوى السطر والفاتورة والإقرار.

#### بوابة القبول G4

- اجتياز أداة/بيئة التحقق الرسمية لكل أنواع المستندات المستخدمة.
- 100% من سيناريوهات clearance/reporting الحرجة ناجحة.
- توقيع مختص ZATCA والمحاسب الضريبي على مصفوفة المتطلبات.
- لا توجد فاتورة إنتاج ببيانات بائع أو رقم ضريبي افتراضي.

### المرحلة 5 — نظام الإدارة والجودة وسلامة الغذاء

**المدة:** 4–6 أسابيع  
**الهدف:** جعل النظام داعماً فعلياً لـISO 9001 وISO 22000/HACCP دون ادعاء شهادة تلقائية.

#### الأعمال

- سجل مخاطر وفرص، أهداف جودة، مؤشرات واتجاهات.
- ضبط الوثائق: المالك، الإصدار، الاعتماد، تاريخ النفاذ، والأرشفة.
- برامج PRP، تحليل المخاطر، CCP/OPRP، الحدود الحرجة، الرصد والانحراف.
- عدم المطابقة وCAPA: السبب الجذري، الإجراء، المسؤول، الموعد، والتحقق من الفعالية.
- شكاوى العملاء، تقييم الموردين، الاستدعاء، والتتبع.
- التدقيق الداخلي ومراجعة الإدارة وخطط الإجراءات.
- سجل التدريب والكفاءة والتنبيه لانتهاء الشهادات.
- خطة طوارئ وتشغيل مستمر للحوادث البيولوجية والبيئية والتقنية.

#### بوابة القبول G5

- تمرين استدعاء ناجح يحدد كل العملاء والدفعات المتأثرة خلال ساعتين.
- إغلاق ≥ 90% من إجراءات CAPA في موعدها أثناء التجربة.
- تنفيذ تدقيق داخلي كامل وإغلاق جميع حالات عدم المطابقة الكبرى.
- مراجعة فجوات من مختص ISO/HACCP؛ الشهادة الخارجية مسار مستقل.

### المرحلة 6 — PDPL والأمن والجاهزية المؤسسية

**المدة:** 3–4 أسابيع  
**الهدف:** إثبات حماية بيانات العملاء والموظفين والقدرة على الاستجابة للحوادث.

#### الأعمال

- جرد البيانات وتصنيفها وتحديد الغرض والأساس النظامي ومدة الاحتفاظ.
- إشعارات خصوصية، إدارة الموافقات عند الحاجة، وطلبات الوصول/التصحيح/الإتلاف.
- تشفير النقل والتخزين والنسخ، وإدارة مفاتيح منفصلة عن البيانات.
- RBAC دقيق وفصل الواجبات ومراجعة صلاحيات ربع سنوية.
- سجل غير قابل للعبث للعمليات الحساسة.
- Threat Model وSAST وفحص حزم واختبار اختراق.
- خطة استجابة للحوادث، أدوار الاتصال، حفظ الأدلة وتمرين مكتبي.
- سياسة احتفاظ وإتلاف تشمل السجلات والنسخ والسجلات الفنية.

#### بوابة القبول G6

- صفر ثغرة حرجة/عالية، وخطة زمنية للمتوسطة.
- تنفيذ طلب صاحب بيانات تجريبي ضمن المهلة الداخلية المعتمدة.
- نجاح تمرين حادث وفقد جهاز واستعادة خدمة.
- توقيع مسؤول الخصوصية/المستشار على مصفوفة PDPL.

### المرحلة 7 — هندسة الإصدار والدعم التجاري

**المدة:** 3–4 أسابيع  
**الهدف:** تحويل البرنامج إلى منتج يمكن تثبيته وترقيته ودعمه بأمان.

#### الأعمال

- حزمة تثبيت موقعة رقمياً، وتحقق من checksum ومصدر التحديث.
- ترقية تلقائية أو موجهة مع rollback وهجرة قاعدة قابلة للاستعادة.
- سياسة إصدارات ودعم وإصلاحات أمنية وEOL.
- ترخيص المنتج وشروط الاستخدام وسياسة الخصوصية واتفاقية الدعم/SLA.
- مراقبة صحية، سجلات منظمة، وتجميع أعطال بموافقة العميل ودون بيانات حساسة.
- دليل تثبيت ومسؤول نظام ومستخدم ومحاسب ودليل استعادة.
- آلية تذاكر وتصنيف P0–P3 ومسار تصعيد.
- اختبار توافق Windows والشاشات والطابعات واللغة العربية.

#### بوابة القبول G7

- تثبيت/ترقية/rollback ناجح على مصفوفة الأجهزة المستهدفة.
- توقيع الحزمة صالح ولا توجد ملفات تطوير أو بيانات تجريبية داخلها.
- تدريب الدعم وحل ثلاثة حوادث محاكاة ضمن SLA.
- اكتمال الوثائق التجارية والقانونية والتقنية.

### المرحلة 8 — UAT والتشغيل التجريبي والإطلاق

**المدة:** 6–8 أسابيع  
**الهدف:** إثبات الأداء في مزرعة فعلية قبل التعميم.

#### الأسابيع 1–2: قبول المستخدم

- سيناريوهات يومية وشهرية وسنوية ببيانات مجهولة أو مصطنعة واقعية.
- توقيع ملاك العمليات: إنتاج، مخزون، مبيعات، مشتريات، HR، محاسبة وجودة.

#### الأسابيع 3–6: Pilot

- تشغيل متوازٍ مع النظام/السجلات الحالية.
- مطابقة يومية للمبيعات والمخزون، وأسبوعية للحسابات، وشهرية للإقرار.
- اجتماع عيوب يومي لأول أسبوعين ثم مرتين أسبوعياً.

#### الأسابيع 7–8: قرار Go/No-Go

- مراجعة المؤشرات والمخاطر وخطة الرجوع.
- تجميد الإصدار، نسخ كامل، تدريب، وخطة دعم مكثف لمدة أسبوعين.

#### بوابة الإطلاق G8

- صفر P0/P1 لمدة 14 يوماً متصلة.
- UAT الحرج 100% والإجمالي ≥ 95%.
- إقفال شهر تجريبي ومطابقته واعتماده من المحاسب.
- نجاح 100% لفواتير ZATCA ضمن نطاق العميل المستهدف.
- استعادة كاملة ضمن RTO وRPO.
- توقيع Go-Live من مالك المنتج، القائد التقني، QA، المحاسب، الأمن، والعميل التجريبي.

## 7. نموذج لوحة المتابعة الأسبوعية

| الحقل | الوصف |
|---|---|
| رقم المتطلب | مثال `ACC-023` أو `ZATCA-041` |
| الوصف | نتيجة أعمال قابلة للاختبار |
| الأولوية | Must / Should / Could |
| المالك | شخص واحد مسؤول |
| المرحلة/البوابة | G0–G8 |
| البداية/الاستحقاق | تاريخان محددان |
| معيار القبول | Given/When/Then أو نتيجة رقمية |
| رابط الدليل | اختبار، تقرير، PR، لقطة، توقيع |
| الحالة | Not Started / In Progress / Blocked / Review / Done |
| نسبة الإنجاز | 0، 25، 50، 75، 100 فقط |
| المخاطر/العوائق | وصف وتأثير وتاريخ حل |

### قواعد الحالة

- `Done` تعني أن معيار القبول اجتاز وأن الدليل مرفق وأن المراجع وافق.
- `Blocked` أكثر من يومي عمل يتطلب تصعيداً ومالك حل وتاريخاً.
- لا تتجاوز الأعمال الجارية مهمتين لكل مطور لتقليل التشتت.
- أي انحراف زمني أكبر من 10% يستلزم خطة تصحيح، لا مجرد تغيير التاريخ.

## 10. قائمة Go-Live النهائية

- [ ] جميع البوابات G0–G8 موقعة.
- [ ] بناء Release قابل لإعادة الإنتاج وموقع رقمياً.
- [ ] لا P0/P1 ولا ثغرات عالية/حرجة.
- [ ] قاعدة الإنتاج فارغة من بيانات Demo والحسابات الافتراضية.
- [ ] النسخ والاستعادة والمراقبة والتنبيهات تعمل.
- [ ] الإقفال المحاسبي التجريبي معتمد.
- [ ] ZATCA ناجح للعميل والنطاق المستهدف.
- [ ] مصفوفة SOCPA/IFRS وPDPL مكتملة ومراجعة.
- [ ] التدريب والأدلة وSLA وقنوات الدعم جاهزة.
- [ ] خطة rollback وأسماء أصحاب القرار وأرقام الاتصال موثقة.
- [ ] موافقة كتابية من العميل التجريبي ومالك المنتج.

## 11. تعريف النجاح بعد الإطلاق

يتم تقييم الإصدار بعد 30 و60 و90 يوماً:

- توفر ≥ 99.5%.
- صفر فقد بيانات وصفر قيد غير متوازن.
- نجاح ZATCA ≥ 99.5% من أول إرسال، و100% بعد إعادة المحاولة.
- إغلاق P1 ضمن SLA بنسبة ≥ 95%.
- رضا المستخدمين ≥ 80%.
- انخفاض وقت إعداد التقارير الشهرية ≥ 40% عن خط الأساس.
- تطابق المخزون والحسابات ≥ 99%، مع تفسير واعتماد كل فرق.
- قرار موثق: تعميم، تمديد Pilot، أو إيقاف ورجوع.
