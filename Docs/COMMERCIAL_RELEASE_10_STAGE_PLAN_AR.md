# خطة الوصول إلى النشر التجاري — AquaFarm Pro

**الإصدار:** 1.0  
**تاريخ الاعتماد الأولي:** 11 أغسطس 2026  
**الحالة الحالية:** Beta متقدمة؛ غير معتمدة بعد للنشر التجاري الكامل  
**النطاق المستهدف:** إصدار Windows مستقر لمزرعة واحدة أولاً، ثم التوسع فقط بقرار معماري مستقل.

## قواعد تنفيذ الخطة

- لا تبدأ مرحلة قبل اجتياز بوابة المرحلة السابقة وتوثيق دليل الاجتياز.
- كل متطلب يجب أن يملك مسؤولاً، أولوية، معيار قبول، اختباراً ودليلاً محفوظاً.
- أي عيب يهدد سلامة البيانات أو المحاسبة أو الضريبة أو الاستعادة يصنف P0 ويوقف الإصدار.
- يمنع وصف النظام بأنه متوافق أو معتمد من SOCPA أو ZATCA أو PDPL دون مراجعة واعتماد متخصص مؤهل.
- تحفظ أدلة كل بوابة في `Docs/ReleaseEvidence/Stage-N/` عند التنفيذ.

## المرحلة 1 — تثبيت خط الأساس وحوكمة المصدر

**الهدف:** إنشاء نقطة بداية نظيفة وقابلة للتتبع.

**الأعمال:**

- مراجعة التعديلات الحالية وتقسيمها إلى commits مترابطة بعد اعتماد مالك المنتج.
- منع العمل المباشر على `main`، واعتماد فروع `codex/` أو فروع ميزات ومراجعة Pull Request.
- تثبيت SDK عبر `global.json` وتوحيد NuGet ومجلدات البناء.
- توثيق نموذج النشر المدعوم: جهاز واحد/مزرعة واحدة/SQLite.
- إعداد سجل مخاطر وسجل قرارات معمارية وسجل متطلبات مرقم.

**بوابة الخروج G1:** استنساخ نظيف ينجح فيه `restore`, `build`, و`test`، ولا توجد تغييرات مجهولة أو ملفات تشغيل ضمن المصدر.

## المرحلة 2 — بناء وإصدار قابلان لإعادة الإنتاج

**الهدف:** ضمان أن أي جهاز CI نظيف يستطيع إنتاج الحزمة نفسها.

**الأعمال:**

- إصلاح مسار NuGet fallback وعمليات restore المعلقة.
- تثبيت إصدارات الأدوات والحزم وإنشاء lock files عند ملاءمتها.
- تشغيل Debug وRelease وPublish على Windows نظيف.
- تفعيل معاملة التحذيرات المهمة كأخطاء وإضافة تحليل ساكن.
- إنتاج artifacts مرقمة مع checksum وبيانات commit والإصدار.

**بوابة الخروج G2:** خمسة تشغيلات CI متتالية ناجحة، وبناء Release نظيف بلا أخطاء، وإمكانية إعادة إنتاج المثبت من tag محدد.

## المرحلة 3 — إغلاق الفجوات الوظيفية وتجميد النطاق

**الهدف:** منع عرض وظائف ناقصة أو نجاحات وهمية للمستخدم.

**الأعمال:**

- إكمال ربط الموظفين والشهادات والمستخدم المسجل في سجلات الجودة والموارد البشرية.
- استكمال دورة المشتريات والاستلام والمخزون والطباعة والربحية end-to-end.
- جرد كل شاشة وزر وتقرير وتصنيفها: مكتمل، جزئي، معطل، أو خارج الإصدار.
- إزالة TODO وplaceholder والرسائل التي توحي بنجاح عملية لم تنفذ.
- تجميد نطاق الإصدار الأول بعد اعتماد مالك المنتج.

**بوابة الخروج G3:** لا توجد وظيفة ظاهرة بلا تنفيذ واختبار قبول، وكل دورة حرجة تعمل بعد إغلاق التطبيق وإعادة فتحه.

## المرحلة 4 — سلامة قاعدة البيانات والمعاملات

**الهدف:** حماية القيود والمخزون والسجلات من الفقد أو التناقض.

**الأعمال:**

- اختبار جميع migrations من قاعدة فارغة ومن نسخة سابقة ومن نسخة تشغيل فعلية مجهلة.
- مراجعة المعاملات والذرية والقيود والفهارس والدقة العشرية والتزامن.
- فرض ثوابت المحاسبة والمخزون في طبقة الخدمة وقاعدة البيانات قدر الإمكان.
- اختبار انقطاع التطبيق والطاقة أثناء الحفظ والترحيل والاستعادة.
- تحديد حدود SQLite ومنع فتح الملف عبر مشاركة شبكية غير مدعومة.

**بوابة الخروج G4:** صفر فقد بيانات في اختبارات الفشل، نجاح الترقية والrollback، وتطابق المخزون والقيود بنسبة 100% في سيناريوهات القبول.

## المرحلة 5 — الأمن والخصوصية وإدارة الهوية

**الهدف:** الوصول إلى خط أساس أمني مناسب لبيانات العملاء والموظفين.

**الأعمال:**

- مراجعة RBAC لكل شاشة وعملية حساسة على مستوى الخدمة، لا الواجهة فقط.
- اختبار القفل والجلسة وتغيير الدور وإعادة تعيين كلمة المرور وسجل التدقيق.
- إزالة الأسرار والبيانات التجريبية من المصدر والحزمة والسجلات والوثائق.
- حماية مفاتيح ZATCA والشهادات، ووضع سياسة تدوير وإبطال ووصول.
- إعداد تصنيف بيانات وسياسة احتفاظ وحذف وتصدير ومعالجة حوادث وفق PDPL بعد مراجعة قانونية.
- إجراء SAST وفحص حزم واختبار اختراق ضمن نطاق تطبيق سطح المكتب.

**بوابة الخروج G5:** صفر ثغرات حرجة/عالية مفتوحة، واختبارات صلاحيات ناجحة، واعتماد مختص الأمن والخصوصية.

## المرحلة 6 — صحة المحاسبة والضريبة وZATCA

**الهدف:** إثبات صحة النتائج قبل استخدامها كسجل رسمي.

**الأعمال:**

- مراجعة دليل الحسابات، القيود، الفترات، الإقفال، العكس، العملات، VAT والتسويات.
- بناء عينات ذهبية يقارنها محاسب سعودي مرخص يدوياً.
- اختبار XML وUBL وQR والتوقيع والتسلسل والأرشفة وحالات الرفض وإعادة الإرسال.
- اجتياز onboarding وعينات ZATCA الرسمية في البيئة المناسبة.
- توثيق حدود المسؤولية وعدم تسويق أي اعتماد قبل الحصول عليه.

**بوابة الخروج G6:** تطابق محاسبي وضريبي 100% للعينات الحرجة، نجاح اختبارات ZATCA الرسمية، وتوقيع قبول من المختصين.

## المرحلة 7 — الاختبارات الشاملة والأداء وتجربة المستخدم

**الهدف:** إثبات الجودة تحت الاستخدام الحقيقي وليس نجاح البناء فقط.

**الأعمال:**

- قياس Coverage للمنطق الحرج مع هدف 85% للمحاسبة والضريبة و70% للخدمات الحرجة إجمالاً.
- إضافة اختبارات تكامل وواجهة وRTL وDPI والطباعة والتصدير والثقافات العربية والإنجليزية.
- اختبار قواعد كبيرة وتقارير طويلة وتسرب الذاكرة والاستجابة والإلغاء.
- منع الاستثناءات الصامتة وإضافة معرف خطأ آمن للمستخدم وسجل تشخيص منظم.
- اختبار الاستخدام مع موظفين فعليين وتصحيح مشاكل الوصول وسهولة التعلم.

**بوابة الخروج G7:** نجاح 100% للسيناريوهات الحرجة و95% إجمالاً، صفر P0/P1، وتحقيق أهداف الأداء المعتمدة.

## المرحلة 8 — النسخ الاحتياطي والاستعادة والتشغيل

**الهدف:** ضمان استمرارية العمل وقابلية استعادة البيانات فعلياً.

**الأعمال:**

- اختبار النسخ المشفر والتحقق من checksum والاستعادة والrollback على جهاز آخر.
- توفير نسخة خارج الجهاز دون مسار ثابت خاص ببيئة المطور.
- تحديد RPO وRTO وتوثيق Runbook للاستعادة والكوارث.
- إضافة مراقبة حجم القاعدة، المساحة، فشل النسخ، سلامة القاعدة وأخطاء التطبيق.
- تنفيذ تمرين استعادة دوري وتسجيل نتيجته.

**بوابة الخروج G8:** ثلاث عمليات Backup/Restore متتالية ناجحة، RPO لا يتجاوز 24 ساعة وRTO لا يتجاوز 4 ساعات، مع تنبيه موثق عند الفشل.

## المرحلة 9 — التغليف والقانون والدعم وPilot

**الهدف:** تحويل البرنامج إلى منتج قابل للتثبيت والدعم والتعاقد.

**الأعمال:**

- اختبار المثبت والترقية والإزالة والrollback على Windows 10 و11 وحساب غير إداري حيثما أمكن.
- إضافة EULA وترخيص المنتج وإشعارات تراخيص الطرف الثالث وسياسة الخصوصية.
- توحيد README ودليل المستخدم والترميز والمصطلحات على SQLite والنطاق الفعلي.
- إعداد آلية تحديث موقعة، سياسة إصدارات، قناة دعم، SLA وخطة rollback.
- تنفيذ Pilot لمدة 4–6 أسابيع في مزرعة واحدة ببيانات مجهلة وخطة رجوع.

**بوابة الخروج G9:** قبول Pilot موقع، نجاح التثبيت والترقية والاستعادة، وعدم وجود P0/P1، واكتمال الحزمة القانونية والتشغيلية.

## المرحلة 10 — اعتماد وإطلاق ومراقبة ما بعد النشر

**الهدف:** إصدار تجاري مضبوط يمكن إيقافه أو التراجع عنه بأمان.

**الأعمال:**

- اجتماع Go/No-Go يضم المنتج والتقنية وQA والمحاسبة والأمن والتشغيل.
- إنشاء tag نهائي وحزمة موقعة وchecksums وRelease Notes وقائمة عيوب معروفة.
- نشر تدريجي لعميل أو موقع واحد ثم التوسع بعد فترة مراقبة.
- مراقبة الأعطال والأداء والنسخ الاحتياطية ودقة القيود والمخزون.
- تحديد آلية hotfix، ومسؤوليات الاستجابة، ومراجعة بعد 7 و30 و90 يوماً.

**بوابة الخروج G10:** توقيع جميع أصحاب الاعتماد، نجاح النشر التجريبي والمراقبة، وتوفر rollback مجرب قبل توسيع الانتشار.

## ترتيب الأولويات الفوري

1. إصلاح البناء النظيف وNuGet وتثبيت الـbaseline.
2. مراجعة التعديلات الحالية وتجميد نطاق الإصدار.
3. إغلاق الوظائف الناقصة ومنع النجاح الوهمي.
4. إثبات migrations وسلامة البيانات والنسخ والاستعادة.
5. اعتماد المحاسبة وZATCA والأمن قبل أي ادعاء تجاري.

## تعريف الجاهزية النهائية

لا يعد التطبيق جاهزاً للنشر التجاري إلا بعد اجتياز البوابات العشر، وتوفر أدلة قابلة للمراجعة، وعدم وجود عيوب P0/P1، ووجود موافقات مكتوبة من مالك المنتج وQA والمحاسبة والأمن والتشغيل.
