# المرحلة الرابعة — سلامة قاعدة البيانات والمعاملات

**التاريخ:** 12 أغسطس 2026  
**الحالة:** مكتملة تقنياً؛ تحقق CI معلق

## الضوابط المنفذة

- قاعدة SQLite محلية فقط؛ يرفض التطبيق مسارات UNC والمشاركات الشبكية صراحةً.
- كل connection string ينشئه التطبيق يفرض foreign keys، وضع `ReadWriteCreate`، ومهلة اتصال مضبوطة.
- بدء التشغيل يطبق migrations ثم يفحص: pending migrations، `integrity_check`، و`foreign_key_check`.
- تفعيل WAL و`FULL synchronous` ومهلة انتظار 30 ثانية عند التحقق من قاعدة التشغيل.
- توحيد النسخ اليدوي في الإعدادات على `BackupService` الآمنة: snapshot online، تشفير DPAPI، SHA-256، وفحص integrity.
- الاستعادة تتحقق من checksum والملف المرشح، تنشئ نسخة pre-restore، وتعيد القاعدة السابقة إذا فشلت الاستعادة.

## أدلة القبول

- ترقية قاعدة فارغة إلى آخر migration.
- ترقية أول schema محفوظ مع بقاء سجل عميل سابق.
- downgrade لآخر migration ثم إعادة الترقية بنجاح.
- رفض نسخة احتياطية عُدّل محتواها دون تغيير بيانات القاعدة الحية.
- نجاح فحص WAL والمفاتيح الأجنبية بعد بدء التشغيل.
- اختبارات المعاملات القائمة تغطي ذرية الاستلام والمخزون والترحيل والمطابقة المحاسبية.
- نتيجة المجموعة المحلية بعد الإضافات: `157/157` عند اكتمال التشغيل النهائي المتوقع.

## حدود التشغيل المعتمدة

- الإصدار الأول محطة Windows واحدة وقاعدة SQLite محلية؛ التشغيل المتزامن عبر مشاركة شبكة غير مدعوم.
- النسخ المشفر مرتبط بمستخدم Windows الحالي عبر DPAPI. النقل إلى جهاز أو حساب آخر يحتاج إجراء ترحيل مفاتيح/نسخة تصدير معتمدة في مرحلة التشغيل.
- لا ينفذ downgrade على قاعدة إنتاج مباشرة؛ الرجوع التشغيلي يتم باستعادة نسخة pre-deployment متحققة. اختبار `Down` مخصص لإثبات قابلية rollback في قاعدة معزولة.
- يجب أن تكون النسخة الخارجية المطلوبة متصلة وقابلة للكتابة قبل بدء التطبيق في بيئة Production وفق الإعداد الحالي.

## قرار G4

تعد G4 مكتملة تقنياً عند نجاح CI على commits المرحلة. أي فشل في build أو tests أو الحزمة الحتمية يعيد فتحها حتى المعالجة.
